# Across the app

**The questions that make something say what they make, and the ones that rename say only the name.** A word is worth explaining at the moment somebody is asking for it — which is when they reach for the control that makes one — and never before: nobody can decide when they want a second Dashboard until they have used the first for a while, so a screen at sign-in would demand the decision in the one moment it cannot be made. A rename is about something already in front of you and explains nothing.

**One menu, however it opens.** Every menu in the app — a row's, a tab's, a Panel's — offers the same shape: same entries, same look, and an entry that cannot be chosen stays visible and says why, rather than disappearing. A row opens its by the same control every time it appears: a vertical triplet of dots, one size, one hover and focus treatment, drawn rather than typed because `···` is punctuation whose size and baseline belong to the font. Three dots therefore always mean a menu, never a link that navigates. A tab or a Panel opens its own instead — right-click, a long press, or the keyboard's own menu key — because the tab or the Panel itself is already the trigger.

**Deleting anything asks first, in a dialog, and the row or tab it was asked from does not change.** The question names what is going and what goes with it — for a Workspace, how many Items stop being visible — and offers Cancel and Delete in one fixed order everywhere, so the control under the pointer never changes meaning between the press that asks and the press that answers. Escape and Cancel are the two ways to say no; pressing outside is deliberately not one. Focus returns to where it was asked from, and where that has gone with the thing deleted, to the tab you are now on. Nothing is sent until Delete is pressed, and a Workspace's Delete waits for the count it is asking about, though a count that could not be read at all lets it through rather than trapping you. A refusal keeps the dialog open and says why. Editing is not destructive and asks nothing, but shares the form's shape: it also opens over the page and returns the focus to what it came from.

**Editing more than one field at a time happens in a form, and a form is a modal with a route of its own**, dimmed behind. The URL says what is open, so the back button closes it and a link opens it — which is what a question does not need and does not get: a question is a small centred dialog with nothing to link to. Nothing is written until **Save**, which sends only the fields that actually changed, so leaving one untouched cannot overwrite an edit made elsewhere. Cancel, Escape and pressing outside all close the form and discard what was typed, without asking, because Cancel means cancel. Deliberately unlike the deleting rule above: a delete asks because there is one way to say yes and no way back, while a form has Save sitting in it, unpressed. **The route is for a form opened from content** — an Item, which somebody may want to link to. A form opened from a tab or from a row of the Types window is a detour from what you are already looking at, so it has no address of its own; everything else about it is the same.

**Ordering** puts rows in the order you choose by dragging one, wherever a list can be reordered.

**Live updates** carry a change made in one place to everywhere else it is shown, without a reload.

**Selection** picks several rows out of one list to act on them together, from anywhere on a row rather than a control of its own. Started by whichever door the device has — a ctrl/cmd-click, or a finger resting on the row until it is picked out — and from the first row on a pointer adds or removes one row at a time with ctrl/cmd, or reaches a span with shift; a finger has a tap in place of ctrl/cmd, since it has no such key, and no span. One list at a time holds a selection; a row that leaves the list leaves it; and while one is held, every row's own menu and swipe step aside for it, so acting on one row cannot happen while several are picked — except a routing suggestion's own chip, which is a carve-out. A plain click always opens the row it lands on, ending whatever selection was held first; where none was, it is simply what opens a row. What is picked is acted on one row at a time, so an action can stop part way and say so, leaving what did not happen still picked.

**Updating** picks up a new version of Cockpit. A tab running one older than the server can read nothing it is told, so it stops, fetches the newer one and comes back where you were, rather than asking. Your sign-in and your work are untouched; the version is the only thing that was wrong. Where there is no newer one to fetch, it says so instead of trying again. **A tab can also be behind without being told so**: Cockpit is fetched in parts, and a deploy while a tab is open takes away the parts it has not fetched yet — so a description whose formatting never arrives offers the new version rather than taking it, the description being editable and saveable in the meantime and a reload being able to throw away what you are part-way through.

Binding on anything written to be read as a description of the product, test names included (see "Tests are named in the product's language" in `docs/testing-strategy.md`).
