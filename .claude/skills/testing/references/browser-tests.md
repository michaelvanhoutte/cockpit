# Browser tests (F3)

Open this when writing, changing or debugging a walk under `tests/e2e/`. The rules every test follows are in [SKILL.md](../SKILL.md); this file adds what only a walk needs.

## Writing a walk

- **Before adding any walk, read the F1 rules for that area.** Where the proposition is already stated there, the walk is duplication; where only part of it is, the rest belongs on a walk already standing, not on one of its own.
- **A walk proves one behaviour.** Extend a walk only with assertions on the behaviour its title names. A new behaviour gets its own `test()`, under the `describe` of the behaviour it builds on, or its own `describe` where it builds on none.
- **A walk with no rule around it has no statement to review**, so keep the shape SKILL.md's "Name it after the product, not the mechanism" gives with nothing skipped: an area straight to a case is a missing `describe`, not a badly named one.
- **Name a spec `*.test.ts`**, not Playwright's `.spec.ts`, or `tools/test-explorer` will not count it.
- **Take `test` from `./support/app`**, never `@playwright/test`: one imported directly opts out, silently, of the guard that tells "the stack went away" from "this walk is broken".
- **Arrange through the commands API; assert through the UI.** Reaching a state through the capture box, menus and dialogs costs seconds that prove nothing about the title. Put the app in the state the walk needs with `tests/e2e/support/arrange.ts` (`giveToTheInbox`, `giveADashboard`, `giveToAPanel`), which sends the browser's own commands as the signed-in person (`page.request` carries the page's cookies), then open the page, since a page already open learns of new rows only through the live-updates stream, which the Live updates area owns. Drive through the UI only what the title names. A state the API cannot express is a decision to take, never a test-only seeding route added quietly.
- **Capturing through the UI is Capture's alone.** `capture(...)` outside the `Capture` area fails `scripts/lib/e2e-conventions.mjs`. The walks not yet rewritten are listed there, each held at the number of captures it makes today, so the list only shrinks; a walk on it is rewritten to the rule when next touched.
- **Never rely on another walk having run.** CI deals walks across four shards by individual walk (`fullyParallel`, one worker per shard), so the walks in one file run in any order and on different shards. A walk that relies on an earlier one is a bug, fixed where found. A shard dealt no walk passes.
- **Assert on rows the walk created, never on totals**, since walks in one run share the stack's storage.

## Wait for the change, not for the picture of it

The cause of every intermittent CI failure so far has been a walk acting on something the browser had drawn but not yet sent or read back: a resize drawn on every pointer move and saved only when the hand stopped, cancelled by a reload; and, twice, a workspace switched but not yet loaded, where the one being left stays on screen and usable, so the next capture went to it. A dashboard drag has the same shape today: the arrangement is drawn before it is sent, so the panels look identical either side of the save.

- **Where something on screen tells "drawn" from "kept", wait on that; where nothing does, wait on the server's answer** to the command (`answerTo`, `tests/e2e/panels.test.ts`).
- **Every walk that changes workspace goes through `switchTo`** (`tests/e2e/support/app.ts`), which waits for the address to get deeper, since that happens only once the workspace has been read. A walk pressing the tab itself fails `scripts/lib/e2e-conventions.mjs`; the rule is a check because as a comment it was fixed once per walk.
- **Sign in through `signIn`.** The run signs in once per person per project (`tests/e2e/support/sign-in.setup.ts`), and the same check names a walk about anything but signing in that drives the issuer itself. The exception is a walk that signs out, which would end the session every later walk loads, so it signs in through Google itself (`signInThroughGoogle`).

**This class is invisible on a fast machine and shows at once under a slow API.** Delay every call in the `test` fixture (`page.route('**/v1/**', …)` with a 150ms wait) and run the suite. One pass of that found a product bug rather than a walk bug: an item's form opened on text older than the save just made, because a save finished before the workspace had been read back (fixed by drawing a change over the held copy until a read that began after its answer lands: `apps/web/src/changeQueue.ts`). Pinning to two cores also reproduces contention, but on Windows it mostly reproduces a native `node.exe` crash instead.

## Time and size limits

- **A walk takes at most 15 seconds on CI.** Split one that passes it; never give it a longer timeout (`test.slow()`, a raised `timeout`). Every walk has Playwright's 30 seconds, so one near it fails on a slow runner with nothing broken, and the steps it gathered are coverage the test explorer never shows, since it lists a walk's title and not its steps. The time is the typical one the `E2E (F3)` job's list reporter prints beside the walk, not its slowest run, since a busy runner stretches every walk at once.
- **Each product area has a ceiling on its walks, and passing it fails the run.** `browserWalks` in `tools/test-explorer/concepts.json`, beside its area, held by `pnpm test:e2e:ceilings` in each `E2E (F3)` shard ahead of the browser download. It counts from `playwright test --list` rather than the source, since a walk whose cases come from a table is one `test()` call and several walks. It is per area so one area cannot spend another's room. Raise a ceiling in the same pull request as the walk that needs it; an area sitting under its ceiling is reported, which is the prompt to bring it down.
- **Each shard's walks have a time budget**, `e2eShardBudget` in the same file. After its walks each shard runs `pnpm test:e2e:budget`, which fails when the duration Playwright reported (never the job's wall clock) is past it, naming the number, the shard and the duration. It sits at least 30% above the slowest shard's typical, the swing runner load gives a run, so it catches a doubling rather than drift. Raise it in the pull request that needs it, with its `reason` saying what the tier measured.

## The stack

**F3 runs on its own stack with a database rebuilt per run.** `pnpm test:e2e` boots a second copy of the app (`scripts/e2e-stack.mjs`): its own Wrangler and Vite on this checkout's own ports (`scripts/lib/ports.mjs`, so two worktrees can run at once), and its own state directory. The register is restored from a migrated-and-seeded template; each account's own store is created empty by the run's first request, since nothing outside the Worker can write to a Durable Object. So test data never piles up in the development database and development never decides whether a test passes. The restore is a file copy (5ms against 7s for re-running migrations), which is what makes "fresh every run" affordable. Point the suite at a deployed environment with `E2E_BASE_URL`.

**Every spec runs on desktop and phone**, as the Playwright projects `desktop` (mouse, 1280px) and `phone` (touch, 480px), because a capability is claimed to work for a user and the user is on a phone as often as a desk. Both are Chromium: a viewport and input matrix, not a browser matrix; a second engine is a separate decision. An interaction that exists on one form factor only (a swipe, a hover-revealed control) is a different capability with its own spec. This cannot be pushed below F3: the F1 runner is jsdom, which has no layout engine and reports every element as zero-sized, so viewport-dependent rendering and the touch path are unprovable below a real browser.

**One spec holds a real service worker, because the stack cannot.** Vite's dev server registers none, and every upgrade bug so far was in the worker's lifecycle across a deploy. `tests/e2e/updating.test.ts` opens the production build (`apps/web/dist`) from a server of its own (`tests/e2e/support/deployments.ts`) that decides when a deploy lands. Each later deploy is derived from that one build (every asset renamed, the precache manifest rewritten to match) and removes the previous version's files, and the server can hold a version's files mid-download. The server copies Cloudflare's start-page fallback, its redirect of `/index.html` to `/` and file removal, and is not Cloudflare, so looking at staging before promoting stays the check on Cloudflare itself. The spec runs with the `Updating` area and in every full run. **The stack builds `dist` only if missing, so after changing the web app run `pnpm --filter web build`**, or the spec walks the old build.

**A stack that dies mid-run fails the run and says so, once.** Playwright watches its web server only while starting it, so without this every later walk failed on a symptom of its own and read like a dozen unrelated bugs. The stack prints why it went, reading the reason out of Wrangler's own log because what it prints to the terminal is often empty; the walk that finds it gone fails and the rest are skipped naming it. **Nothing is retried and no run turns green**: skipping begins only after something has failed, so a stack going away, which may be the app becoming unstable, is always a red run.

**The transient that killed it is patched out, not tolerated.** `wrangler dev` could quit on a transient it ought to survive ([workers-sdk#15317](https://github.com/cloudflare/workers-sdk/issues/15317)). A pinned `pnpm` patch carries the incident, the reasoning and what a version bump costs (`pnpm-workspace.yaml`). Since that record is now ordinary noise in Wrangler's log, `fatalReason` reads past that one pairing of reason and cause and no other (`scripts/lib/stack.mjs`). The noise the same event makes in the Worker's log is owned by ["Close the live-updates stream quietly when a browser walks away" (issue 128)](https://github.com/michaelvanhoutte/cockpit/issues/128).

**The stack pins every outside credential empty**, so a real key in `apps/api/.dev.vars` cannot reach a walk ([third-parties.md](third-parties.md)).

## Which walks a pull request runs

On a pull request the browser tier runs only the areas whose `sourcePatterns` in `tools/test-explorer/concepts.json` own a changed file (`scripts/ci-e2e.mjs`). It runs every walk when a changed file is in no area, is the registry, the Playwright config or under `tests/e2e/support/`, or forces every package's tests in full. A merge runs them all.
