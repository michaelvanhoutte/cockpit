# Offline / local-first behavior

**Opening draws from the server**, never from the copy this device saved. Nothing shows for 300 ms, then a quiet "Loading…" line. If the server has not answered in 3 s, the request fails outright or the device says it is offline, Cockpit is offline: it draws what was saved, and an answer that comes later replaces it. Capture and the Car view open at once and send when the server answers.

- **Reads offline:** what was saved, where this version can still read it — the Workspaces, Dashboards and Items you have opened, and an Item's history once opened. Files are never saved.
- **Nothing to show** says "Cockpit can't be reached" with *Try again*, and either that nothing is saved here to show, or that what is saved was saved in a shape this version can't read and will be again once you've been online with this version.
- **While offline, every change except a capture is refused** with "You're working offline"; a capture waits in the outbox.
- **The header shows an outlined ● Offline · saved 14:32 pill** left of the account menu while offline, found or chosen, the time being when the Workspace read on screen was saved (dropped on a phone). Pressing it opens the account menu.
- **Offline also starts mid-visit** when a read gets no answer, or the live stream drops and the server cannot be reached; it ends when the server answers again.
- **Work offline**, above Sign out in the account menu on desk and phone, reads **Go online** while offline. Working offline reads nothing from the server, closes the live stream, keeps captures waiting in the outbox, and is remembered on this device (every tab of it follows) until Go online, which also re-reads everything on screen and sends the outbox. A refused change offers Go online. Reloading while working offline opens at once from what was saved, without the 3 s wait.
- New incoming messages only arrive when online.

**Capturing never waits on the connection.** Pressing Capture keeps the note, its files and the time it was captured on this device and empties the box at once; Cockpit sends it in the background, oldest first, as soon as a connection gets through — on opening, on reconnecting, on coming back to the tab, on the next capture, after anything else reaches the server, and every half-minute to a minute in between. The Item says when it was captured, not when it arrived.

- **One line under Capture's form** shows what has not landed, and survives a reload: *1 waiting to send*, or *1 not sent* with the server's reason and **Put back**, which returns the note and its files to the box; each is drawn only while there is one. **Undo** on a capture still waiting deletes it, so nothing is sent ("Undo a capture back into the box, in place of the Just captured list", issue 1104). A capture is *Not sent* only when the server refuses it — its Workspace deleted meanwhile, or a Type named by a capture an older build queued; no connection, a timeout, a server error or an expired sign-in keep it waiting.
- **The Capture tab carries a count** while anything has not landed, a refused one included.
- **A waiting capture belongs to whoever captured it.** It is sent and shown only while they are signed in, an expired sign-in loses nothing, and only signing out deletes it — after asking, when anything is waiting ("2 captures haven't been sent and will be lost"). A recording Write could not transcribe is theirs on the same terms, offered with Retry only to them, and counted in the same question ("1 recording hasn't been transcribed and will be lost").
- **Where the browser cannot keep it** — a private window, storage refused — capture sends at once, and with no connection says so and leaves the note in the box.

A Panel's **+** (*Add an item to <Panel>*) opens Capture, so an Item added from it waits offline with its Panel like any capture. Every other change still needs the connection; queuing those, and reconciling the local copy once a source exists to reconcile against, are designed, not built: see "Offline writes and reconciliation" in `docs/ideas.md`.
